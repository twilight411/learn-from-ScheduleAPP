# 植物页首屏慢：三层根因与压测方法论

---

## 简历写法（可直接用）

**植物页首屏性能排查与压测（ScheduleApp）**

- 针对用户反馈「登录快、植物页慢」，编写 **Python 压测脚本** 复现 Flutter `PlantProvider` 调用顺序（串行雷达+生图，并行周报/果实），量化冷/热路径与 **5 并发登录**。
- 通过 **外网 vs 服务器 loopback** 对照（`tree/weekly` 外网 143ms / 本机 **12ms**），判定瓶颈在 **同步 LLM + 即梦生图**，非 CPU/内存（load **0.01**）。
- 拆解三层根因：① Flutter Web 首包 **~10MB+**（CanvasKit wasm **7.1MB**）；② `tree/weekly` 首次 **6 次 LLM**（**9.89s**）；③ 生图无缓存首次 **10–17s**；客户端串行+并行叠加 **12–15s**。
- 输出三轮压测报告与 JSON 原始数据，驱动后续 Fast API、DB 缓存、异步生图等改造；优化后植物页 API 合计约 **0.35–0.45s**（缓存命中）。

---

## 遇到的问题

用户反馈：**首次进入 App / 植物页很慢**；登录后 `users/me`、`schedule/today` 仅 **6–13ms**，植物相关极慢。

| 接口 | 优化前耗时 |
|------|------------|
| `GET /tree/weekly` | 首次 **9.89s**，二次 **2.13s** |
| `GET /tree/weekly/image` | 首次 **10.03s**，二次 **0.011s** |
| `GET /fruits/image` | 首次 **16.58s**，二次 **0.009s** |

---

## 我做了什么

1. **梳理真实调用链**（对照 `PlantProvider._loadAllData`）  
   - 串行：`tree/weekly` → `tree/weekly/image`  
   - 并行：`reports/weekly` ∥ `fruits/image`  
   → 任一慢接口都会拉长「页面加载完成」感知。

2. **编写可复现压测**（`.deploy/api_load_benchmark.py` 等）  
   - 冷路径：`refresh=true` 测最坏生图  
   - 热路径：连续 3 轮无 refresh  
   - 并发：5 用户同时登录看 p50  

3. **分层对照实验**  
   - 外网：含 RTT，模拟用户  
   - loopback：`127.0.0.1:8000`，剥离公网  
   - 资源：`free`、`uptime`、`uvicorn` RSS  

4. **写报告与数据归档**  
   - 基线 / 果实缓存后 / round2 复测  
   - 避免「感觉快了」无据可查

## 面试要点（详细）

### Q1：你如何证明「不是服务器不够强」？

**答：**

- **资源面**：压测时 load average **0.01~0.04**，available 内存 **~1.3GB/1.9GB**，uvicorn RSS **~110MB**，无 OOM、无 CPU 打满。  
- **对照面**：同一台机 `tasks` loopback **11–12ms**，说明进程与 DB 正常。  
- **嫌疑面**：慢接口集中在 **LLM（DeepSeek）** 与 **即梦**，耗时 **秒级且稳定重复**（refresh 时 ~10s），符合外部 API 特征，不像 CPU 饱和的随机抖动。

**追问：如果 load 很低但 RT 很高怎么办？**  
→ 看外网与 loopback 差值；差值大是网络；两边都慢才是应用逻辑。

---

### Q2：压测为什么要模拟「植物页路径」而不是只打单个接口？

**答：**

- 用户感知是**整页**，不是单 API。  
- 串行 + `Future.wait` 会让耗时接近 **相加 / max(并行支)**，单接口压测会**低估或误判**（例如雷达 1.5s + 生图 10s 并行果实 10s → 用户等 ~11s 而非 1.5s）。  
- 应用层脚本按业务顺序发请求，才能对齐 **12–15s** 的首屏体验。

---

### Q3：冷路径和热路径为什么要分开测？

**答：**

| 类型 | 含义 | 典型用途 |
|------|------|----------|
| **冷路径** | `refresh=true` 或首次无缓存 | 评估最坏体验、成本（即梦 QPS/费用） |
| **热路径** | 日常打开、DB 命中 | 评估真实用户 80% 场景 |

我们冷路径生图 **~10s** 可接受（后台/强制刷新）；热路径必须 **&lt;500ms** 级。

---

### Q4：「列表秒级抖动」怎么理解？算性能 bug 吗？

**答：**

- **抖动**：`GET /tasks` 多数 **~100–300ms**，偶发 **1.7–6s**（热路径第 2 轮）。  
- loopback 任务列表 **11ms** → 服务端逻辑不慢。  
- 归因：**公网 RTT、TCP、并发登录、压测脚本连续打满** 等噪声。  
- **不算稳定后端瓶颈**；若产品要求可上 CDN、连接复用、HTTP/2、区域部署，但与本植物页 **10s 级** 问题量级不同。

---

### Q5：二次打开为什么快？是内存缓存吗？

**答：**

- 主要是 **持久化**：`SpiritWeeklyScore`、`weekly_tree_images`、`monthly_fruit_images` 等表已有数据。  
- 重启 uvicorn 后二次仍快 → 不是进程内存缓存。  
- 面试可补充：客户端还有 `PlantWeekCache` 内存缓存，减少重复请求，但**压测 hit 的是服务端 DB**（`tree_image_cache_hit` 日志）。

---

### Q6：你作为开发/负责人，如何向产品解释「还要 10s」？

**答：**

- **首次**或**强制刷新**生图：即梦物理耗时 **~10s**，与优化无关。  
- 优化目标是：**日常打开** 先出雷达和占位/旧图（**&lt;0.5s API**），生图后台完成再替换。  
- 用压测报告里的 **cached=true / 143ms** 与 **refresh 10s** 两张表说明「两种场景」。

---

### 易错点（面试扣分项）

- 只说「加了缓存」不说**指纹**与**失效条件**。  
- 把二次快说成「服务器预热」。  
- 没提 **客户端调用顺序** 导致并行 max(10s)。  
- 压测只有外网、没有 loopback，无法反驳「网络问题甩锅给后端」。
