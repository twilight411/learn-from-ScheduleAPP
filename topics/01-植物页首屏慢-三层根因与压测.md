# 植物页首屏慢：三层根因与压测方法论

## 遇到的问题

用户反馈：**首次进入 App / 植物页很慢**，登录后基础接口很快，但植物相关接口极慢。

实测（优化前，账号「雅」，外网）：

| 接口 | 耗时 |
|------|------|
| `POST /auth/login` | ~0.31s |
| `GET /users/me`、`/profile`、`/schedule/today` | **6–13ms** 级 |
| `GET /tree/weekly`（植物状态） | 首次 **9.89s**，二次 **2.13s** |
| `GET /tree/weekly/image` | 首次 **10.03s**，二次 **0.011s** |
| `GET /fruits/image` | 首次 **16.58s**，二次 **0.009s** |

服务器 CPU/内存/load 均正常 → **不是机器扛不住**。

---

## 根因（三层叠加）

### 第一层：Flutter Web 首包重

- 强制 **CanvasKit**：`canvaskit.wasm` 约 **7.1MB**
- `main.dart.js` 约 **3.3MB**
- 曾出现 wasm **未 gzip**，拖慢「打开页面」本身

### 第二层：植物状态接口同步 LLM

`GET /tree/weekly` 在**首次无周得分**时会：

1. `calculate_all_spirits` → 5 个精灵各 1 次 LLM 点评
2. `build_tree_data` → 再 1 次树叙述 LLM  

合计约 **6 次 LLM**，外网实测首次 **~9.89s**。

### 第三层：生图接口同步即梦

- `tree/weekly/image`、`fruits/image` 无缓存时每次调即梦 **~10–17s**
- 二次快是因为 **DB 已有 `image_url`**（`weekly_tree_images` / 后来的 `monthly_fruit_images`）

客户端 `PlantProvider` 先串行等雷达再生图，再并行周报+果实 → 等待时间**叠加**。

---

## 解决方法

| 层 | 手段 | 效果（数据） |
|----|------|----------------|
| Web | `flutter clean` 全量部署 `build/web`；`renderer: auto`；nginx wasm gzip | 消除 `AssetManifest` 404 |
| 状态 | `tree/weekly` **fast**：跳过 LLM 点评/叙述，后台 `weekly_tree_enrichments` | **9.89s → 143ms**（19:45 压测） |
| 生图 | DB 指纹缓存 + `wait=false` 后台生图 + 轮询 `status` | 日常 **~122–133ms**，`cached=true` |

详见各主题笔记与 [round2 压测报告](../benchmark-reports/api-load-benchmark-2026-05-25-round2.md)。

---

## 压测怎么做的

1. **外网脚本** `api_load_benchmark.py`：冷路径 `refresh=true`、热路径 3 轮、5 并发登录  
2. **日常路径** `api_benchmark_async_paths.py`：`wait=false`、enrichment  
3. **本机 loopback** `server_loopback_bench.py`：排除公网 RTT（`tree/weekly` **12ms**）

**关键对比**：外网慢、loopback 快 → 瓶颈在**业务/外部 API**，不在带宽本身。

## 面试可能怎么问

**Q：你怎么定位「慢在客户端还是服务端」？**  

A：分层测——登录后列表毫秒级说明链路通；对嫌疑接口做**服务器 127.0.0.1** 与外网对比；看资源监控；对植物页按调用链拆（状态 / 生图 / 并行）；用脚本固定账号复现并记录 p50。

**Q：为什么二次打开就快？**  

A：典型**缓存**：生图 URL 落库、LLM 得分落库；不是「服务器预热」，而是**持久化命中**。

**Q：什么叫「列表秒级抖动」？**  

A：同一接口（如 `GET /tasks`）多数 **~100ms**，偶发 **1–6s**；服务器本机 tasks **11ms** → 归因为**公网 RTT/并发噪声**，非稳定后端瓶颈。见 [round2 报告 §8](../benchmark-reports/api-load-benchmark-2026-05-25-round2.md)。
