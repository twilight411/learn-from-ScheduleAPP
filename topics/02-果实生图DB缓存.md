# 果实生图 DB 缓存（monthly_fruit_images）

---

## 简历写法（可直接用）

**果实生图持久化缓存（ScheduleApp）**

- 发现 `GET /fruits/image` 每次走即梦 **~10–17s**，而生命树已有 `weekly_tree_images` 表缓存，果实侧缺失对称设计。
- 新增 **`monthly_fruit_images`** 表与 **`get_or_generate_fruit_image()`**：按 `user_id + year + month + 得分指纹` 命中则直接返回 URL，响应带 **`cached=true`**。
- 压测：果实接口日常 **16.58s → 133ms**；植物页热路径由 **12–15s 降至 1.5–2s**（与生命树缓存叠加）。
- 修复 refresh 路径 **DELETE+INSERT** 在生图耗时窗口内触发 **SQLite UNIQUE** 导致 500（见主题 06）。

---

## 遇到的问题

- 生命树：`weekly_tree_images` 有指纹缓存，二次 **~11ms**。  
- 果实：无表，每次 **16.58s**（含 LLM 选果种 + 即梦）。  
- 植物页并行 `fruits/image` 与 `tree/weekly/image`，果实支拖慢整页。

---

## 我做了什么

1. **对齐生命树缓存模型**  
   - 表字段：`user_id, year, month, fruit_type, image_url, score_fingerprint, image_status`  
   - 指纹：当月任务得分汇总 hash，任务变更则失效重生成  

2. **统一入口 `get_or_generate_fruit_image()`**  
   - 命中：读 DB → 返回 URL + `cached=true`  
   - 未命中：调即梦 → 写 DB → `cached=false`  

3. **与前端契约**  
   - `ApiPlantRepository` 解析 `cached` / `image_status`  
   - 日常请求不带 `refresh`  

4. **压测验证**  
   - 三轮热路径 + `refresh=true` 冷路径分开记录  

---

## 结果

| 场景 | 优化前 | 优化后 |
|------|--------|--------|
| `fruits/image` 日常 | 16.58s | **133ms**（`cached=true`） |
| `fruits/image?refresh=true` | 16.58s | **~10s**（预期，即梦） |
| 植物页 API 合计（缓存） | 12–15s | **0.35–0.45s** |

## 面试要点（详细）

### Q1：缓存 key 怎么设计？任务改了怎么办？

**答：**

- 主键维度：**用户 + 年 + 月**（一月一果）。  
- **score_fingerprint**：对当月完成任务 ID、得分等做稳定 hash。  
- 任务增删改得分 → 指纹变 → 视为 miss，下次生成新图；**不**用「时间 TTL 一天过期」糊弄业务。

**追问：指纹太敏感会怎样？**  
→ 小改动就重绘，成本高；太粗则图与数据不一致。要在产品「何时重画」上对齐（我们跟周报得分绑定）。

---

### Q2：为什么用 DB 不用 Redis？

**答：**

- 生图结果要**跨重启、跨实例**持久；SQLite/Postgres 已存在，运维简单。  
- 读 QPS 低（植物页打开），**单行主键查询**足够，133ms 含网络。  
- Redis 适合高频会话；这里是**月级资产**，DB 更贴切。

**追问：多实例 uvicorn 呢？**  
→ DB 即共享存储；注意 refresh 并发写用 UPDATE 而非 DELETE+INSERT（主题 06）。

---

### Q3：`cached=true` 对前端意味着什么？

**答：**

- 可**立即**展示 `image_url`，无需 loading 10s。  
- 可与 `image_status=pending` 组合：先旧图/占位，后台换新图再轮询（主题 04）。  
- 面试强调：**协议字段驱动 UI**，不是前端猜「是不是第二次」。

---

### Q4：生命树和果实缓存有何异同？

| | 生命树 `weekly_tree_images` | 果实 `monthly_fruit_images` |
|--|---------------------------|----------------------------|
| 粒度 | 周 | 月 |
| 失效 | 周得分指纹 | 月得分指纹 |
| 优化前 | 二次已快 | 每次 16s |
| 优化后 | 122ms | 133ms |

---

### Q5：如何向面试官证明「缓存生效」？

**答：**

- 响应 JSON 含 **`cached": true`**。  
- 服务端日志 `tree_image_cache_hit` / 果实等价日志。  
- 压测：同一用户连续 3 轮，第 1 轮慢、第 2–3 轮 **&lt;200ms**。  
- **重启 uvicorn** 后仍快 → 非内存缓存。

---

### Q6：refresh 和日常请求的区别？

**答：**

- **日常**：只读，命中 DB。  
- **refresh=true**：用户主动换图，必须调即梦，**~10s** 正常；实现上应用 **UPDATE** 同一行，避免 UNIQUE（主题 06）。

---

### 易错点

- 只说「加了表」不说**指纹失效**。  
- 认为缓存会导致 500（实际是 **写库策略** 问题，不是读缓存）。  
- 果实与生命树**并行**时只优化了一边，植物页仍慢。
